# 2026-10-03 — 실측 보고서 결함 전량 수리 착수

> 상태: **진행 중** / 관련: [[../_HOME]] · `docs/awt_project_analysis_and_strategy.md` §10-3·§11-9

## 발단

대표님이 물으신 것은 **"AWT를 플러그인으로 만들 가치가 있는가"**였습니다. 조사 결과 **질문의 전제가 틀렸습니다** — AWT는 이미 네 표면에 올라가 있습니다(MCP Registry `io.github.ksgisang/awt` v1.7.1 활성, Smithery, Claude Code 플러그인, Agent Skill). 따라서 실제 질문은 **"이미 올라간 자리에 추가 투자를 할 가치가 있는가, 그 투자를 제품 결함 수리보다 앞에 둘 이유가 있는가"**였습니다.

## 결정

**유통이 아니라 주장을 고치는 데 투자합니다.** 등재는 현 상태로 유지하고, 1~2순위가 끝난 뒤에 홍보를 재개합니다.

근거 세 가지:

1. **플러그인 표면에서는 돈이 나오지 않습니다.** Anthropic 1차 문서·약관·블로그 전수 확인 — 수수료도 수익배분도 유료등재도 없고 로드맵에도 없습니다. 유통 경로일 뿐입니다.
2. **유통은 이미 확보되어 있고 유지 비용이 0입니다.** 추가 투자가 필요하지 않습니다.
3. **간판 주장 세 가지가 현재 성립하지 않습니다.** 자가수복은 기본 모드에서 작동하지 않고, 시각 매칭이라는 차별점은 실사용에서 0회 발화했으며, 결함을 찾아낸다는 주장은 9일간의 유일한 실증에서 입증되지 않았습니다.

지금 홍보에 자원을 쓰면 **"등재되었으나 작동하지 않는 52%"** 통계에 합류합니다. 디렉터리 등재는 무료이고 영구적이지만 나쁜 첫인상의 비용은 그렇지 않습니다. 반면 Stacklok 조사에서 테스트 생성과 QA 자동화는 MCP 용도 1·2위이므로 **수요는 기다려 줍니다.**

## 콜드 스타트가 찾은 2건을 1순위로 승격

보고서를 쓴 뒤 배포본 1.7.1을 빈 가상환경에 설치해 신규 사용자 경로를 그대로 걸었습니다(§11). 보고서가 놓친 결함 세 건이 **첫 5분 안에** 나왔고, 그중 둘을 1순위로 올립니다.

### ① `aat run`이 종료코드 0으로 끝난다 (§11-4)

TTY가 없으면 승인 게이트에 막혀 **한 단계도 실행하지 않는데** 코드가 0입니다. CI에서는 "테스트 0건 실행 → 파이프라인 녹색"이 됩니다.

**이것을 1순위로 올린 이유는 우선순위 계산이 아니라 일관성입니다.** AAT-109는 *"헛클릭은 PASSED가 아니다"*를 세우고 `StepStatus.WARNING` + 종료코드 3까지 만들었습니다. 그 원칙을 **실행 안에서는 지키고 프로세스 경계에서는 어기고 있었습니다.** 그리고 이것은 §9-5에 적힌 사용자의 인계문과 같은 실패입니다 — ***"「통과했다」가 「검사했다」를 뜻하지 않는다."***

### ② `navigate` + `critical: true`는 반드시 거짓 실패한다 (§11-5)

신규 사용자가 쓸 법한 **가장 단순한 대본**이 1단계에서 죽었습니다.

```
CRITICAL: No screen change (9.1%) after critical click (threshold 50.0%)
URL: https://example.com/        ← 이동은 성공했습니다
PAGE_TITLE: Example Domain       ← 페이지도 떴습니다
FIX_TARGET: scenarios/SC-001_smoke.yaml   ← 멀쩡한 대본을 고치라고 지시합니다
```

이동을 **"critical click"으로 채점**해 클릭용 화면변화 임계값(50%)을 들이댔고, 흰 바탕 페이지라 9.1%만 변해 치명 실패가 됐습니다. `critical: true`만 떼면 즉시 통과합니다(검증 완료).

**그리고 실패가 반복되면 AWT Cloud 유료 제품을 권합니다.** 자기 결함으로 만든 실패 위에 돈을 받으려 하는 모양이 되므로, 마켓플레이스에서 이 장면이 첫인상이 되면 회복이 어렵습니다.

### ③ `aat doctor`가 거짓 초록불을 준다 (§11-6, 2순위)

Playwright가 요구하는 Chromium **빌드 번호**를 보지 않습니다. 결정적으로 **고장 났을 때와 고친 뒤의 출력이 완전히 동일**했습니다. 그 ✓는 정보를 담고 있지 않으며, 사용자는 초록불을 믿고 진행했다가 다음 명령에서 실행 실패를 만납니다.

## 제가 틀렸던 것 — 기록으로 남깁니다

`assert_text`가 *"Text 'Example Domain' not found ... via OCR"*로 실패했을 때 저는 이것을 **AWT 결함으로 보고했습니다.** 같은 블록이 `Title: Example Domain`을 찍고 있었으니 모순이라고 읽은 것입니다.

**틀렸습니다.** example.com이 개편되어 "Example Domain"은 이제 `<title>`에만 있고 `<h1>`은 없으며 화면에 렌더링되지 않습니다(HTML 직접 확인). **OCR이 정확했고 제 대본이 틀렸습니다.**

다만 결함이 아닌 자리에서 교훈 두 개가 남습니다.

- 진단문이 `Title: ...`을 출력한 **바로 아래 줄에서** `not found`라고 말합니다. 같은 블록의 두 문장이 서로를 부정하는 것처럼 읽히며, **실제로 저를 오독으로 이끌었습니다.** 제목과 본문을 구분해 표기해야 합니다.
- `assert_text`가 DOM이 아니라 **눈에 보이는 픽셀**을 검사한다는 사실이 문서에 없습니다. 설계로서는 오히려 더 엄격합니다(숨겨진 DOM 텍스트에 속지 않습니다). 이것은 README에 적을 **장점**이지 숨길 일이 아닙니다.

## 포지셔닝 — 이번 수리의 판정 기준

실측이 가리키는 정직한 정체성은 **"증거를 남기는 결정론적 웹 E2E 러너"**입니다. "AI가 스스로 고치는 자율 QA"가 아닙니다.

하늘고 사례에서 두 결함을 찾아낸 것은 **사람의 눈**이었지만, 그 사람이 볼 수 있는 **사진을 남긴 것은 AWT**였습니다. AWT는 속도를 내주고 증거를 받는 거래를 하며, 이것은 결함이 아니라 설계 선택입니다. 11단계 52초 중 상당 부분이 증거 수집 비용이고, 평범한 Playwright라면 3~5초에 끝날 일입니다.

**따라서 모든 수리는 하나의 질문으로 판정합니다** — *"헛클릭은 통과가 아니다"가 이 표면에서도 지켜지는가.*

## 작업 방식

- 단위 작업마다 **로컬 시험 → 커밋 → 푸시 → CI 성공 확인 → 텔레그램 보고**.
- 결함 수정에는 **역변이 시험**을 붙입니다. 시험이 실제로 그 결함을 잡는지 확인하지 않으면 통과는 증거가 아닙니다(§7-2에서 927개 녹색과 15% 커버리지가 공존한 이유).
- 세 표면(CLI·스킬·MCP)에 걸친 변경은 동시에 반영합니다.
