# 다른 세션에 AWT 테스트를 의뢰하는 매뉴얼

이 기기에서 돌아가는 **다른 프로젝트의 Claude Code 세션**(자내공, 하늘고스터디앱 등)에게
AWT로 실제 사이트를 시험해 달라고 맡길 때 쓰는 문서입니다.
아래 **§2 브리핑 전문**을 통째로 복사해 그 세션에 붙여 넣으면 됩니다.

이 문서가 정본입니다. 같은 내용을 매번 새로 작성하지 말고 이 파일을 갱신하십시오.
갱신 시점과 방법은 §4에 적어 두었습니다.

---

## 1. 왜 브리핑이 따로 필요한가

AWT 자체는 이미 전역에 설치되어 있고 전역 스킬도 등록되어 있으므로,
다른 세션은 아무 준비 없이 바로 시험할 수 있습니다.
그런데 **맨 `aat`를 호출하면 어떤 빌드가 실행될지 보장되지 않습니다.**
브리핑은 그 한 가지를 눌러 주기 위해 존재합니다.

측정된 사실은 다음 세 가지입니다.

**첫째, 전역 `aat`는 작업 트리를 직접 가리킵니다.**
`/usr/local/bin/aat`의 셔뱅이 `#!/usr/local/opt/python@3.14/bin/python3.14`로 못 박혀 있고,
그 인터프리터는 `_aat_devqa.pth`를 통해 `aat`를 이 저장소의 `src/aat/`로 해석합니다.
그래서 절대 경로로 부르면 **커밋하지 않은 변경까지 포함한 지금 이 작업 트리**가 실행됩니다.
가상환경을 활성화한 상태에서도 셔뱅이 이깁니다(실측 확인).

**둘째, 낡은 사본이 실재합니다.**
`DSL(Dr.StrangerLoop)/.venv` 안에 AWT **1.5.0**이 복사되어 있습니다.
그 환경에서 맨 `aat`를 부르면 수개월 전 코드가 조용히 돌아갑니다.

```
$ "DSL(Dr.StrangerLoop)/.venv/bin/python" -c "import aat; print(aat.__version__)"
1.5.0
$ "DSL(Dr.StrangerLoop)/.venv/bin/python" -c "import aat.engine.sweep"
ModuleNotFoundError: No module named 'aat.engine.sweep'
```

**셋째, 버전 문자열로는 구별할 수 없습니다.**
저장소의 `pyproject.toml`도 `1.7.1`이고 PyPI에 올라가 있는 `aat-devqa`도 `1.7.1`인데,
그 사이에 미배포 커밋이 서른 개 넘게 쌓여 있습니다(AAT-112부터 AAT-121까지).
따라서 `aat --version`이나 `doctor`의 "AWT CLI v1.7.1"은 최신 여부를 판별해 주지 못합니다.
**신뢰할 수 있는 것은 모듈 경로뿐**이고, 그래서 브리핑 `[2]`가 경로를 직접 출력시킵니다.

> 전역 스킬(`~/.claude/skills/awt/SKILL.md`)에는 `which aat || (pip install aat-devqa && ...)`라는
> 설치 안내가 들어 있습니다. 하필 그 `which aat`가 위의 1.5.0 사본을 집어 올리고,
> 설치 쪽으로 가면 낡은 사본을 하나 더 만듭니다.
> **브리핑 `[1]`이 이 줄을 명시적으로 덮습니다.** 스킬을 동기화해도 이 항목은 남겨 두어야 합니다.

## 2. 브리핑 전문 (이 블록을 복사하십시오)

`[0]`의 URL만 세션에 맞게 채우면 나머지는 그대로 쓸 수 있습니다.

```text
[0] 대상: <여기에 URL을 적습니다>

[1] AWT 실행 경로 — 반드시 절대 경로를 쓰십시오.
    /usr/local/bin/aat ...        ← 이것만 사용
    mcp__awt__* 도구               ← 이것도 안전(전역 등록, 저장소 직결)

    맨 `aat`는 쓰지 마십시오. 가상환경에 따라 수개월 전 1.5.0 사본이 잡힙니다.
    `aat --version`으로 최신 여부를 판단하지 마십시오. 저장소본과 배포본이
    똑같이 1.7.1이라 구별되지 않습니다.
    `pip install aat-devqa`를 실행하지 마십시오. 스킬 문서에 그 줄이 있지만,
    이 기기에서는 낡은 사본을 하나 더 만드는 결과가 됩니다.

[2] 시험 전 확인 (1회):
    /usr/local/opt/python@3.14/bin/python3.14 -c "import aat, aat.engine.sweep as s; from aat.core.models import ScreenshotSpace; print(aat.__file__); print('sweep', s.MAX_SCREENS)"

    기대 출력:
      /Users/apple/Documents/Projects/AI_Auto_Tester/src/aat/__init__.py
      sweep 10

    다르게 나오거나 ModuleNotFoundError가 나면 낡은 빌드입니다. 멈추고 보고하십시오.

[3] 절차 — 네 단계를 순서대로 지키십시오.
    1 SCAN:     /usr/local/bin/aat scan --url <URL>  → 요약 보고 → 승인 대기
    2 GENERATE: 시나리오 YAML 작성 → 보여주고 → 승인 대기
    3 EXECUTE:  /usr/local/bin/aat run --skill-mode --fast <scenario>
                → 실패하면 즉시 중단하고 보고 → 지시 대기
    4 REPORT:   결과 요약

    금지: `aat devqa`, `-y`/`--auto-approve`, 승인 없는 실행,
          지시 없는 코드·시나리오 자동 수정, 승인 절차 우회.

[4] 이번에 중점적으로 확인할 것 (최근 수리된 부분입니다):
    - 같은 단정이 어느 단계에서 불리든 같은 판정을 내는가.
      → AWT 자기 진행 막대가 판정 대상 DOM 안에 있어서, 막대에 찍힌 기대값
        글자를 AWT가 "화면에 보인다"고 읽던 결함을 고쳤습니다(AAT-123).
        막대에 나오는 문구를 `text_visible`의 기대값으로 한 번 써 보십시오.
        통과하면 결함이 되살아난 것입니다.
    - `find_and_type`의 대상이 <select>·readonly·disabled이거나 입력 후에도
      비어 있을 때 WARNING(종료코드 3)으로 찍히는가. 통과로 찍히면 결함입니다.
    - 실패한 단계 이후의 단계가 UNVERIFIED로 빠지고 통과율에서 제외되는가.
      → 일부러 깨지는 시나리오(없는 계정으로 로그인 등)를 한 번 돌려 보십시오.
    - 첫 화면 밖(스크롤해야 보이는) 요소를 찾아내는가.
      → 시나리오에 `scroll` 단계를 손으로 넣지 마십시오. 넣으면 이 기능이
        작동했는지 알 수 없게 됩니다.
    - 선택자가 깨졌을 때 이전 실행이 적립한 사진으로 요소를 찾아내는가.
    - 캔버스·이미지에 그려진 글자를 `text_visible`이 OCR로 읽어내는가.

[5] 보고 내용 (이 세션에서 대표님께 직접 보고합니다):
    - 통과/실패/경고/미검증 건수를 따로 적으십시오.
      "24스텝 중 22 통과"처럼 미검증을 통과에 합산한 수치는 쓰지 마십시오.
      실패가 있었다면 첫 실패 단계 번호와 그 뒤 미검증 건수를 적습니다.
    - .aat/last_run.json 경로, reports/ 경로
    - 로그에 다음 문구가 찍혔는지 (각각 어느 단계에서인지 함께):
        "below the fold"  /  "healed_from_bank"  /  "satisfied by OCR"
        "not counted"  /  "text went nowhere"
    - 거짓 통과로 의심되는 단계가 있으면 그 근거
```

### Flutter 웹(CanvasKit) 대상일 때 덧붙일 문장

하늘고스터디앱이나 ClasRing처럼 Flutter 웹을 시험한다면 `[4]`에 아래를 더하십시오.

```text
    - Semantics 라벨 기반 find_and_click / find_and_type가 동작하는가.
      → 손좌표(click_at)로 대체하지 마십시오. 실측으로 뒤집힌 옛 조언입니다.
    - 시나리오에서 wait 단계를 전부 빼고도 통과하는가.
      → AWT가 폰트 로딩과 다시 그리기를 기다리도록 고쳐 두었습니다(AAT-117·118).
    - 증거 스크린샷의 한글이 □□□(두부)로 깨지지 않고 또렷한가.
```

## 3. 전역 스킬 동기화

다른 세션이 읽는 스킬은 `~/.claude/skills/awt/`이고, 정본은 저장소의 `awt-skill/awt/`입니다.
둘은 자동으로 맞춰지지 않으므로 기능을 추가하거나 스킬 문서를 고친 뒤에는 손으로 복사해야 합니다.

```bash
SRC=/Users/apple/Documents/Projects/AI_Auto_Tester/awt-skill/awt
DST=~/.claude/skills/awt

cp -a "$DST/SKILL.md" "$DST/SKILL.md.bak-$(date +%Y%m%d)"   # 되돌릴 수 있게
cp "$SRC/SKILL.md" "$DST/SKILL.md"
rm -rf "$DST/references" "$DST/templates"      # 지우고 다시: 아래 설명 참조
cp -a "$SRC/references" "$SRC/templates" "$DST/"

diff -r --exclude='*.bak-*' --exclude=scripts "$DST" "$SRC" && echo "동일합니다"
```

`SKILL.md` 본문이 `references/` 세 파일과 `templates/` 두 파일을 직접 가리키므로
**하위 디렉터리까지 함께 복사해야 합니다.** 본문만 복사하면 링크가 전부 끊어집니다.
(`scripts/`는 비어 있어 복사 대상이 아닙니다.)

먼저 지우는 이유가 두 가지입니다.
`cp -a 원본디렉터리 대상디렉터리`는 **대상이 이미 있으면 그 안으로** 복사해
`references/references` 같은 중첩을 만듭니다. 그리고 지우지 않으면
저장소에서 **삭제된 파일이 전역에만 남아** 두 쪽이 조용히 갈라집니다.
`diff -r`가 그 두 경우를 모두 잡아내므로 마지막 줄을 생략하지 마십시오.

전역 사본은 저장소본과 **바이트 단위로 같게** 유지하십시오.
이 기기에만 해당하는 사항은 전역 사본을 손보는 대신 §2 브리핑에 적습니다.
그래야 다음 동기화가 손질한 내용을 조용히 지우지 않습니다.

### 미결 사항

`awt-skill/awt/SKILL.md`의 머리말이 아직 `version: 1.5.0`입니다(실제 꾸러미는 1.7.1).
저장소본 자체의 표기 오류이고, **`1.8.0` 배포 때 함께 고치기로 했습니다.**
그 파일은 공개 저장소의 `.claude-plugin/marketplace.json`이 직접 가리키는 자리라
배포와 묶어 처리하는 편이 안전합니다.

## 4. 이 문서를 갱신하는 시점

| 무엇이 바뀌면 | 이 문서에서 고칠 곳 |
|---|---|
| 매칭·치유·OCR 등 **시험으로 확인해야 할 기능**을 추가하거나 수리했을 때 | §2 `[4]` 중점 항목을 새 기능으로 교체하고, 로그에 찍히는 문구를 `[5]`에 반영 |
| 새 결함을 고쳐서 **옛 조언이 뒤집혔을 때** | 해당 항목을 지우지 말고 "실측으로 뒤집혔다"고 적어 두기(다른 세션이 옛 습관을 되살리지 않도록) |
| `aat run`의 기본 플래그나 승인 절차가 바뀌었을 때 | §2 `[3]`, 그리고 `CLAUDE.md`의 AWT Testing Workflow |
| 전역 설치 경로나 인터프리터가 바뀌었을 때 | §1의 세 가지 사실, §2 `[1]`·`[2]` |
| `1.8.0`을 배포해서 PyPI본과 저장소본이 갈라졌을 때 | §1 "셋째" 항목의 버전 숫자, §3 미결 사항 |

`[4]`는 **매번 새로 쓰는 자리**입니다. 직전 작업에서 고친 것을 적으십시오.
오래된 항목을 그대로 두면 다른 세션이 이미 확인이 끝난 기능을 다시 재고,
정작 새로 고친 자리는 아무도 밟아 보지 않게 됩니다.
